# HWPML nested-table collision captures

> **Status:** Capture-only artifacts are prepared for coordinator review. No Rust adapter or shared-builder behavior is changed in this branch.

## Question

When a HWPML `CELL` containing a nested table cannot attach its structured blocks to the cell identified by its source coordinate and flat text, the legacy parser searches the built grid row-major for an unclaimed cell with equal flat text and spans. If it finds none, it silently omits those blocks while retaining flat text. If it finds a duplicate elsewhere, it attaches the nested blocks to that other cell. Capture these branches before deciding whether any broader Rust policy should change.

The current private Rust slice deliberately fails with `UNSUPPORTED_FORMAT` when the shared rich builder cannot attach every nested payload to its exact, unchanged source anchor. The capture work does not authorize weakening that fail-closed behavior. Any future adapter decision belongs to a separately reviewed implementation change.

## Future Rust acceptance boundary

Until coordinator review authorizes a separate adapter change:

- Preserve strict 200-column / 10,000-row / 2,000,000-logical-cell shared limits, existing 50 MiB XML input cap, 256 MiB lowering meter, and table nesting limit. These tiny captures do not justify limit changes.
- Keep exact source anchors as the only successful structured attachment. If an ambiguous nested payload cannot be attached exactly, return a typed existing error; never silently omit structure or guess a destination.
- A future capture-backed test may compare complete public result blocks and assert those fail-closed decisions separately. Do not compare only flattened text, which can hide missing or misattached nested structure.
- Do not edit the H0 fixture/capture corpus, shared builder, IR, public parser registration, Cargo files, or publication status in this capture-only branch.
